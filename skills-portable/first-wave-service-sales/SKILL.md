# first-wave service sales

**Preferred activation (operator):** say **`first-wave sales`**. **Aliases:** **`service outreach wave`**, **`send-stage sales`**, **`reply routing`**, **`first batch outreach`**.

## Purpose

Move a bounded service offer from planning into real market contact without letting the offer widen into generic consulting.

This skill is for the first live wave:

- shortlist
- first sends
- first replies
- call handoff
- proposal handoff

It is not for enterprise CRM design or long-term sales operations.

## Core rule

Treat real contact as the objective.

Do not use more planning to avoid sending.

## Best-fit use cases

Use this skill when:

- the offer already exists
- the package is already priced
- there is at least one proof packet or evidence surface
- the operator needs a first batch, not a full go-to-market machine

Do not use it when:

- the offer is still vague
- the buyer type is still unclear
- no recurring pain can be named
- the real task is product design, not service sales

## Required distinctions

Keep these separate:

- public seed target versus qualified lead
- internal demo proof versus client proof
- polite interest versus workflow-qualified reply
- call curiosity versus proposal fit

If the language blurs these, narrow it.

## Workflow

1. **Check send readiness**
   - confirm the offer is bounded
   - confirm the package is visible
   - confirm the proof boundary is explicit
   - confirm the ask is one bounded next step

2. **Shape the first batch**
   - choose close-fit prospects only
   - prefer:
     - clear recurring pain
     - reachable contact path
     - small-team authority
     - visible AI or workflow sprawl
   - remove prospects that require a long philosophy lecture

3. **Draft the first note**
   - personalize the first sentence
   - name one workflow pain only
   - keep the ask to:
     - send the one-pager
     - send the packet
     - take the short call

4. **Run the send check**
   - no invented proof
   - no enterprise transformation language
   - no more than one pain thesis
   - follow-up date chosen before send

5. **Log the contact**
   - record send date, version, channel, anchor, ask, and next follow-up
   - update the live pipeline on the same day

6. **Route the first reply**
   - curious but vague -> send packet
   - asks for details -> send page or packet
   - names workflow -> route to call
   - wants software only -> hold proof-first boundary
   - too early -> park cleanly
   - explicit no -> close cleanly

7. **Capture objections**
   - classify each objection:
     - fit
     - framing
     - package
     - timing
     - proof
   - update the offer only when patterns repeat

8. **Hand off only when earned**
   - call only after one recurring workflow is plausible
   - proposal only after the call makes workflow, authority blur, and package fit concrete

## Good signals

- the prospect responds to the workflow pain, not just the topic
- the prospect asks for the page or packet
- the prospect can name a recurring workflow quickly
- the prospect recognizes hidden review or trust work

## Weak signals

- praise for the idea with no workflow named
- general AI curiosity
- requests for broad education
- pushes toward custom software before proof

## Never do

- Do not call a prospect list pipeline proof.
- Do not call internal demos client validation.
- Do not widen the offer because the first reply is vague.
- Do not send a proposal before workflow fit is earned.
- Do not hide silence by logging planning as traction.

## Success condition

The first wave produces real stage movement:

- `idea` to `sent`
- `sent` to `reply`
- `reply` to `call`

and the operator can explain why each movement happened without inflating the evidence.
