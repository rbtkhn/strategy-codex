# Graceful constraint reporting

**Preferred activation (operator):** say **`graceful report`**. **Aliases:** **`constraint-safe brief`**, **`degraded reporting`**, **`report under thin evidence`**.

## Purpose

Keep automated briefs and summaries trustworthy when:

- evidence is incomplete,
- a preferred source is stale,
- regeneration is missing,
- the public message is cleaner than the underlying state deserves.

This skill is about report discipline, not report style.

## When to use

- You are building or revising a generated brief, digest, dashboard summary, or team update.
- The system draws from mixed-confidence sources.
- There is a risk that the public layer may sound stronger than the evidence layer.
- The operator asks for a trustworthy automated update rather than a fluent one.

## Core rule

Design the report to narrow under pressure, not to bluff under pressure.

## Main distinctions

Keep these separate:

- **authority surface** versus **derived surface**
- **operator digest** versus **public message**
- **proof** versus **self-report**
- **internal demo proof** versus **client proof**
- **public seed target** versus **qualified lead**
- **historical snapshot** versus **current state**

If the report blurs those, it is already drifting.

## Workflow

1. **Name the authority**
   - what source or surface actually owns the fact?
   - what is only a summary, convenience view, or rebuildable artifact?

2. **Check failure modes**
   - abundance-only design
   - graceful degradation
   - silent drift
   - visible abstention

3. **Classify each claim**
   - direct artifact / source-backed
   - operator-observed but not public
   - self-report
   - inference

4. **Decide what survives into the public layer**
   - artifact-backed claims may be stated directly
   - weaker claims should be narrowed, attributed, or turned into a follow-up ask
   - sales claims must stay one rung below the strongest real evidence

5. **Lower the public tone before raising the confidence**
   - if uncertainty rises, confidence in style should fall first

6. **Make the degradation visible**
   - say when evidence is still being confirmed
   - route back to source or artifact collection
   - prefer one narrow ask over a broad synthetic story

## Public-layer rules

The public-facing message may be:

- shorter
- less technical
- more direct

But it must not be:

- more certain
- more current
- more complete
- more authoritative

than the operator digest that generated it.

The same rule applies to sales copy, proof packets, and outreach notes.

## Good fallback moves

- "Most of this movement still needs artifact-linked confirmation."
- "We have setup motion, but not proof-level completion yet."
- "Reply with one screenshot or URL so we can verify the next step."
- "This is still a partial view; use it to route the next action, not to declare success."
- "This is internal workflow proof, not paid-client proof yet."
- "These are public-fit targets, not qualified leads."

## Bad fallback moves

- "The cohort is fully activated" when the signal is mostly introductions.
- "This is the current state" when the dashboard is stale.
- "The system is working well" when the operator still had to rescue the hard part.
- "The offer is validated" when only internal demos exist.
- "The pipeline is strong" when names exist but no outreach has been sent.
- using motivational language to hide verification gaps

## Digest/public split

Always prefer a two-layer pattern:

### Digest layer

Internal:

- source list
- confidence notes
- stale or missing conditions
- action routing

### Public layer

External:

- short pulse
- movement lines
- action wedge
- reply format

The digest explains why the message is allowed to say what it says. The public message does not get to claim more than that.

## Sales and outreach surfaces

Use this same doctrine when the output is:

- a sales page
- a proof packet
- a case study
- a prospect list
- an outreach draft
- a pipeline update

In those cases:

- distinguish internal demonstration from client delivery
- distinguish candidate fit from live demand
- distinguish polite interest from workflow-qualified reply
- narrow the promise before widening the scope

## Verification questions

Before shipping a generated brief, ask:

1. Which claims are directly source-backed?
2. Which claims are still self-report or inference?
3. What source is stale, missing, or only weekly?
4. What would be overclaim today?
5. If I removed the polished phrasing, would the structure still be honest?
6. Am I turning internal evidence into market evidence by tone alone?

If question 5 is no, the report still depends on style more than discipline.

## Never do

- Do not let a dashboard timestamp silently confer authority.
- Do not treat derived freshness as equivalent to source truth.
- Do not compress digest uncertainty away just because the public layer is short.
- Do not treat graceful fallback as a failure; it is the correctness test.

## Success condition

The report remains useful when conditions degrade, and the operator can still trust the message as a routing surface instead of a confidence performance.
