# Abundance-Native Ventures

Use this skill to turn abundance-oriented thinking into governed, evidence-driven outputs.

Keep three levels distinct:

1. venture theory
2. bounded commercial wedge
3. live sales motion

Do not let a strong concept pretend it is already a sellable offer.

## Core posture

- Treat abundance as a decision lens, not a denial of constraint.
- Prefer creation, coordination, stewardship, optionality, and dignity over defensive scarcity framing when the evidence supports it.
- Keep outputs approval-first: propose, do not edit the Record directly.

## Supported requests

1. **Abundance-native idea generation**
   - Produce a small set of high-leverage venture ideas.
   - Ground each idea in lived experience, available tools, and visible evidence.

2. **One-afternoon venture sprint**
   - Return a compact starter package.
   - Include concept, target user, first actions, validation, monetization, and an approval-packet skeleton.

3. **Bounded commercial wedge**
   - Translate repo or lane assets into one narrow paid offer.
   - Name buyer, recurring pain, package shape, evidence boundary, and first proof path.

4. **First-wave sales motion**
   - Turn a bounded wedge into a small live-sales stack.
   - Include shortlist logic, outreach angle, proof packet logic, and the next real contact step.

5. **Approval packet drafting**
   - Draft host-ready approval text for adding an operating paradigm, skill, or library item.
   - Keep the proposal balanced: benefits, risks, counterarguments, duplicate-lane check, and evidence required.

6. **Skill-card drafting**
   - Produce a concise skill card for abundance-native venture work.
   - Keep it portable and reusable outside strategy-codex.

7. **Daily / weekly operator brief**
   - Summarize relevant signals, opportunities, and one small governed experiment.

## Workflow

1. **Identify the output**
   - Ask which artifact is needed if the request is ambiguous.
   - Prefer the smallest useful artifact.

2. **Check the evidence base**
   - Use only the canonical surfaces and current context.
   - If evidence is thin, say so and narrow the claim.
   - Check whether the idea already has an owning lane, note, or experiment before proposing a new surface.
   - Distinguish clearly between:
     - internal workflow proof,
     - public seed targets,
     - real buyer contact,
     - paid client proof.

3. **Choose the commercial level**
   - If the request is exploratory, stay at venture theory.
   - If the request is monetization-focused, force a bounded wedge:
     - one buyer type
     - one recurring pain
     - one package
     - one next proof step
   - If the request is sales-focused, route toward live contact rather than more theory.

4. **Generate the artifact**
   - Keep the first pass concise and paste-ready.
   - Use Markdown unless the host asks for another format.

5. **Preserve governance**
   - Do not stage or merge directly.
   - Do not convert a venture prompt into a Record edit without an explicit approval path.

## Output rules

- Return concrete next actions, not just theory.
- Keep risk visible.
- Do not invent market facts.
- Do not describe internal demos as if they were client proof.
- Do not describe a prospect list as if it were demand.
- Do not rewrite host identity or Record-bearing files unless the host explicitly asks for a proposal or approval path.
- Prefer outputs that can be copied into a proposal, skill card, or brief without reformatting.
- Name duplicate-lane risk explicitly when a new venture idea overlaps an existing lane or skill.

## Evidence ladder for monetization work

When the request moves toward revenue, preserve this ladder:

1. workflow or repo asset
2. bounded offer
3. proof packet
4. outreach target
5. real reply
6. real call
7. real proposal
8. paid client proof

Do not skip rungs in the language.

## When to be extra strict

- If the request mentions `cici-ai`, route through the host's lane docs first.
- If the request mixes identity with venture strategy, separate the identity claim from the operating idea.
- If the request asks for a long simulation, label it as scenario planning, not factual prediction.
