# Singularity-Academy Sprint Proposal Template

non-authoritative. Reusable proposal scaffold.

## Use

Use this after a discovery call confirms that the prospect has one real recurring workflow.

Do not send this before the workflow is named clearly.

## Proposal template

```text
# AI Operating System Sprint Proposal

## Client

- organization:
- owner:
- date:

## Workflow in scope

The sprint will focus on this recurring workflow:

- {name the workflow clearly}

Current pain:

- {one or two sentences on what is breaking now}

## Why this sprint

The goal is not broad AI transformation.
The goal is to make one workflow easier to route, verify, and reuse without losing human authority.

## Sprint outcomes

By the end of the sprint, the client should have:

- one workflow map
- one reporting surface
- one review and receipt contract
- one authority and rollback map
- one operator handoff

## Scope

Included:

- {workflow mapping}
- {brief/reporting layer}
- {review/receipt layer}
- {handoff}

Not included:

- enterprise rollout
- silent posting or execution
- custom software build beyond sprint tooling refinements
- legal, compliance, or employment commitments

## Package

- package: {base sprint / proof-loop sprint}
- fee: {$2,500 / $5,000}

### Base sprint

Best when one workflow is enough.

### Proof-loop sprint

Best when a second workflow, cohort layer, or measured before/after pass is required.

## Working method

Week 1:
- map workflow and authority line

Week 2:
- install reporting layer and proof standard

Week 3:
- install review gate, receipt, and rollback condition

Week 4:
- rerun the loop, compare what changed, and hand off the playbook

## Client responsibilities

- one accountable owner
- access to the current workflow and artifacts
- timely review during the sprint
- willingness to keep scope bounded

## Success criteria

We will consider the sprint successful if:

- the workflow is clearer
- proof standards are more visible
- operator rescue is reduced or made explicit
- the team has one reusable operating surface instead of a one-off draft

## Risks and boundaries

- the sprint improves workflow discipline; it does not guarantee commercial results
- weak source evidence will narrow the output instead of being smoothed over
- the sprint is a service install, not a claim of full automation

## Next step

If this scope looks right, confirm:

1. workflow in scope
2. package
3. start window
```

## Proposal writing notes

- keep the workflow description concrete
- keep scope smaller than the buyer first asks for
- preserve the authority boundary
- do not promise ROI you cannot evidence
- use the language the prospect used on the call
