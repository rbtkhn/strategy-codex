# WUPHF Evaluation

Sovereignty-first evaluation of which WUPHF ideas are worth absorbing into `strategy-codex`.

---

## Summary

WUPHF is best evaluated here as a source of:

- runtime and orchestration patterns
- WORK-layer collaboration ideas
- derived or stage-only substrate concepts

It is **not** a peer memory system for canonical `strategy-codex` notebook state.

In this repo:

- canonical notebook truth stays local
- runtime memory stays rebuildable and subordinate
- agents may derive, stage, or suggest
- agents may not merge or silently promote into canonical notebook surfaces

That means WUPHF notebooks and wiki do **not** map directly to `codex/` durable state. At most, WUPHF-like patterns map to:

- runtime complements
- WORK-layer derived artifacts
- stage-only synthesis packets
- disposable collaborative scratch space

---

## Absorbable Ideas

These are the mechanisms most worth copying, wrapping, or locally recreating.

| Idea | What problem it addresses here | Best local fit | Required governance reinterpretation |
|---|---|---|---|
| **Private scratchpad -> promotable candidate flow** | Analysts and agents need a place to think before writing durable notebook material | WORK scratch, operator notes, stage packets | Recast as WORK scratch -> stage candidate, not notebook truth |
| **Explicit private vs shared memory split** | Polyphonic work needs a clean boundary between local reasoning and group-visible working state | runtime complements, derived observability, temporary shared notes | Shared memory must remain runtime/derived, disposable, and non-canonical |
| **Contradiction / inconsistency detection** | Cross-stream disagreement and judgment-loop tension are hard to track manually | loop/tension derived views, contradiction packets, revisit surfacing | Findings should become warnings or candidate surfaces, not automatic truth |
| **Visible task claiming / work routing** | Multi-agent execution can become opaque or duplicative | WORK-layer orchestration and operator observability | Treat as execution transparency only, not a source of judgment authority |
| **Channelized multi-agent debate** | Polyphonic synthesis benefits from distinct voices arguing in bounded ways | tension briefs, side-by-side packets, derived debate surfaces | Outputs must stay bounded, inspectable, and stage-only unless reviewed |
| **Promotability cues / linting** | Not every agent output deserves durable attention | candidate triage, gate prep, review queues | Reinterpret as “worth staging?” or “needs review?” rather than auto-promotion |
| **Live observability** | Operator trust is higher when derivation is visible | consoles, runtime dashboards, WORK traces | Visibility should explain derivation, not ask the operator to trust hidden agent state |

### Practical read

The strongest absorbable ideas are not “shared agent memory” in the abstract. They are:

- better scratch-to-stage flows
- better contradiction visibility
- better execution observability
- better bounded polyphonic debate surfaces

Those are all compatible with `strategy-codex` doctrine **if** they remain subordinate to local governance.

## Safe Trial Surfaces

Any first experiment should be read-only or stage-only.

### Preferred trial surfaces

- derived WORK-layer loop or tension outputs
- runtime complements
- stage-only synthesis packets
- operator-facing observability surfaces
- disposable notes or artifacts under non-canonical paths

### First wedge

The safest first wedge is:

1. read canonical notebook inputs
2. derive loop, tension, or contradiction outputs
3. write only to derived or disposable surfaces
4. require explicit human review before anything is staged

### Not first-pass targets

Do **not** begin by writing directly into:

- `codex/<year>/<channel>/...`
- durable continuity files
- canonical page, thread, or profile surfaces

The point of an early trial is not to prove that WUPHF can write into the notebook. It is to prove that a WUPHF-inspired mechanism is useful **before** it touches canonical state.

## Non-Absorbable / High-Risk Patterns

These patterns conflict with repo doctrine and should not be adopted directly.

- **Agent-managed shared wiki as quasi-canonical memory**
  - In `strategy-codex`, shared agent memory is not a peer to governed notebook state.
- **Auto-promotion from agent memory into durable notebook surfaces**
  - This violates the repo’s stage-only and human-gated promotion model.
- **Persistent shared memory without explicit disposability and auditability**
  - Hidden memory is a trust and drift problem, not a durable asset.
- **CEO / broker framing as a substitute for Conductor**
  - Conductor is an attention-routing and judgment workflow, not an agent-manager role.
- **Platform dependence that weakens local-first sovereignty**
  - If a vendor or external runtime becomes the real owner of continuity, the design has drifted too far.
- **Agent chatter that increases Theater without better judgment**
  - Visible collaboration is not automatically useful. It can create new Commodity and Theater layers if it generates motion without better calls, better tensions, or better falsification.

These risks are exactly the ones highlighted by repo doctrine around:

- [architecture.md](../architecture.md)
- [sovereignty.md](../sovereignty.md)
- [runtime-vs-record.md](../runtime-vs-record.md)

## Lower-Risk Evaluation Ladder

Replace a platform-integration ladder with a narrower evaluation ladder:

1. **Absorbable ideas**
   - Identify which mechanisms are worth borrowing.
2. **Safe read-only or stage-only trial**
   - Test one or two ideas in derived WORK outputs.
3. **Optional deeper runtime substrate experiment**
   - Only if earlier trials prove useful and sovereignty remains intact.

This keeps the decision centered on selective absorption rather than early platform commitment.

---

## T-C-L-D Read

WUPHF-style systems can help compress some WORK-layer coordination and make multi-agent derivation more visible. But they can also create fresh thin-ice layers if they generate:

- visible but low-value agent coordination
- large shared scratch spaces mistaken for truth
- more outputs without better judgment
- more motion without better falsification

So the test is not whether WUPHF looks advanced. The test is whether any borrowed mechanism improves:

- contradiction visibility
- judgment-loop follow-through
- operator trust
- durable judgment yield per unit of attention

If it does not improve those, it is likely adding Theater or Commodity rather than Durable value.

---

## Recommendation

Treat WUPHF as a **pattern library for WORK/runtime ideas**, not as an integration target by default.

Best first candidates:

- contradiction / tension surfacing
- bounded scratch-to-stage flows
- live derivation observability

Avoid, especially early:

- canonical-memory analogies
- auto-promotion flows
- deep coupling between a shared agent wiki and `codex/` notebook truth

That keeps experimentation useful without weakening `strategy-codex` sovereignty.
