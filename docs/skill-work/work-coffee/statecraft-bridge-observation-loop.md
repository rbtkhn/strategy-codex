# Statecraft Bridge Observation Loop

Use this note to evaluate the first `5-10` real uses of `statecraft-bridge`.

The purpose is to test whether the post-lane bridge actually improves Persia/Iran speaker-to-statecraft routing rather than merely adding one more step.

## What To Record

For each real use, capture:

- date or session anchor
- live claim or named object
- chosen adapter: `Marandi` or `Parsi`
- shared source object opened
- next Iran-lane surface opened
- smooth continuation or reorientation needed
- output shape: positional diagnosis, settlement brief, or transaction handoff
- whether the counterweight check changed the result
- whether the operator immediately bypassed the bridge and asked for direct drafting

## Failure Thresholds

- `3 of first 5` bridge uses needing reorientation = bridge brief or hook wording failure
- repeated Marandi/Parsi confusion on the same class of claim = classification failure
- repeated immediate descent into `state-persia` without bridge use on speaker-heavy objects = bridge hook too hidden or too low-value
- repeated bridge outputs ending in the same lane surface without meaningful branching = adapter distinction too weak

## Refinement Order

If the first batch shows friction, refine in this order:

1. bridge hook wording in the statecraft and Persia front doors
2. bridge brief classification language
3. A-D menu specificity
4. only then expand discoverability to more surfaces
