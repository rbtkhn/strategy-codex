# Speaker Shelf vs Bridge Adapter

WORK only; not Record.

This note defines the constitutional split between the human-facing speaker shelf and the statecraft-facing bridge adapter layer.

Short form:

- `speaker shelf` = notebook object
- `bridge adapter` = retrieval converter

Another short form:

`speaker shelf -> speaker claim -> bridge adapter -> civ-state retrieval -> lane translation -> statecraft output`

## Speaker Shelf

The speaker shelf is a human-facing notebook object.

It owns:

- who the speaker is
- where to open first
- host-role comparison
- support-spine and month-maturity explanation
- provenance bench
- compatibility containment
- citation hygiene for human readers

It should answer:

`How do I read this speaker honestly and efficiently as a notebook object?`

It should not have to secretly perform statecraft retrieval conversion.

## Bridge Adapter

The bridge adapter is a statecraft-facing retrieval converter.

It owns:

- what type of claim the speaker is making
- which `civ-state` retrieval profile that claim should trigger
- which lane surfaces should open next
- what counterweight must be forced before drafting
- whether the output should remain a diagnosis or become a transaction-oriented artifact

It should answer:

`How should this kind of speaker claim change what I retrieve, test, and draft?`

It should not become a biography shelf or a chronology layer.

## Why The Split Matters

If the shelf tries to do both jobs, it bloats into half-statecraft. If the bridge adapter tries to do both jobs, it starts impersonating a speaker notebook.

Without the split:

- shelves become covert drafting surfaces
- bridges start swallowing speaker continuity
- provenance benches get overworked as both evidence stores and routing engines

With the split:

- shelves stay readable
- bridges stay operational
- `civ-state` receives disciplined inputs instead of ad hoc speaker leakage

## Default Handoff Rule

Use the shelf first when the task is still:

- speaker orientation
- month maturity
- host ecology
- provenance lookup
- compatibility or citation hygiene

Use the bridge adapter when the task becomes:

- claim-family classification
- `civ-state` retrieval conditioning
- lane-opening choice for a live strategic claim
- counterweight forcing before statecraft output

If the task is already pure clause design with no need for speaker conditioning, remain on the lane and transaction surfaces rather than detouring through a bridge.

## Macgregor As V1 Exemplar

Macgregor is the cleaner first exemplar because the shelf is already coherent enough to show the split without as much conceptual overload as Mearsheimer.

### Macgregor shelf layer

Macgregor shelf ownership is already legible across:

- `macgregor-arc.md`
- `macgregor-routing.md`
- `macgregor-raw-input-index.md`
- `macgregor-helix.md`
- `macgregor-support-spine-2025-2026.md`
- wrapper front doors such as `README.md` and `index.md`

These surfaces answer who Macgregor is, how his host ecology works, which months are mature, and where provenance lives.

### Macgregor bridge implication

What the shelf should not have to own is the conversion from a live Macgregor claim into:

- claim family
- `civ-state` retrieval profile
- lane opening
- counterweight requirement
- diagnosis versus transaction output

That work belongs in a bridge adapter layer outside the shelf.

## Practical Rule

When the question is `how do I read this speaker?`, stay on the shelf.

When the question is `what should this speaker claim make me retrieve and draft?`, cross the bridge.
