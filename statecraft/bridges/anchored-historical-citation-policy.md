# Anchored Historical Citation Policy

Purpose: govern when historical examples may support statecraft doctrine, bridge notes, lane notes, and transaction-facing analysis without collapsing into vibe analogy, decorative history, or unanchored comparison theater.

Short law:

`historical examples may support doctrine only when they are retrieval-anchored, mechanism-matched, and falsifier-aware`

Hard-gate law:

`no anchored path -> no doctrinal historical claim`

If an example has no anchored retrieval path, it may still appear only as `suggestive analogy`, never as authority-bearing doctrinal support.

## Why This Policy Exists

Statecraft work frequently benefits from historical examples, but the system needs a membrane between:

- raw speaker invocation of an example
- deeper `civ-state` or lane-memory retrieval
- actual doctrinal permission to use the example in analysis or drafting

Without that membrane, history becomes too easy to misuse:

- examples get cited because they sound right rather than because they are retrieval-grounded
- a speaker's mention of a case gets mistaken for doctrinal authorization
- continuity and settlement examples get blurred together until one case is forced to carry the whole object

This policy keeps historical examples mechanism-bearing rather than ornamental.

## Boundary

Keep these layers distinct:

- `civ-lens historical examples audits` = speaker-use evidence and interpretation
- `bridge policy` = doctrine-use permission rule
- `retrieval matrix` = operational example bank for drafting and diagnosis

A speaker mentioning a historical example does **not** automatically make it doctrinally usable. It still needs:

- an anchor tier
- a mechanism match
- a falsifier-aware use condition

## Citation Ladder

### Tier 1: direct lane-memory anchor

The example is explicitly carried by a live lane-local object such as `state-memory`, `peace`, `geo`, `war`, `empire-instrument`, or another lane translation surface.

Use:

- strongest doctrinal support
- best for lane notes, bridge claims, and transaction testing

### Tier 2: `civ-state` scaffold anchor

The example is carried by a `civ-state` scaffold, index companion, or migration synthesis note rather than by a fully translated lane-local object.

Use:

- pattern-level doctrinal support
- best for bridge notes, architecture claims, or comparative retrieval

### Tier 3: legacy `civ-mem` provenance

The example is recoverable from legacy `civilization_memory` provenance and is named in a current object, but has not yet been fully translated into a lane-local or `civ-state` retrieval surface.

Use:

- upstream provenance or provisional support
- best when no stronger translation exists yet

Warning:

- Tier 3 should normally motivate translation work, not permanent reliance

### Tier 4: suggestive analogy only

The example is rhetorically useful but lacks an anchored retrieval path in the current system.

Use:

- exploratory comparison only
- never as doctrinal support

Required label:

- `suggestive analogy`

## Required Checks

Every historical example used for doctrinal support should answer all four checks:

1. **Anchor path**
   What file currently carries the example with enough authority to retrieve it honestly?

2. **Mechanism match**
   What mechanism family is the example actually supporting?
   Example families include:
   - distrust / reversibility
   - settlement inheritance
   - recognition / humiliation
   - corridor governance
   - escalation trap / trap-conditioned bargaining
   - guarantor form / treaty form
   - successor carry / ordinary-governance restatability
   - exclusion / room geometry

3. **Function type**
   What work is the example doing in this argument?
   Common functions:
   - continuity memory
   - warning case
   - settlement precedent
   - guarantor-form precedent
   - counterweight
   - falsifier

4. **Falsifier or misuse warning**
   What would make the example weak, overextended, or misleading here?

If any of those four answers are missing, the example should be demoted until they are supplied.

## Hard-Gate Rule

Examples may support doctrine only when they are:

- retrieval-anchored
- mechanism-matched
- falsifier-aware

Examples may **not** support doctrine when they are:

- unanchored
- used only because they are famous
- carrying a different mechanism than the current claim
- treated as self-validating simply because a speaker invoked them

## Preferred Pairing Rule

When useful, pair:

- one **memory / continuity** example
- one **settlement / architecture** example

This keeps a single case from being forced to carry both civilizational memory and modern institutional design at once.

Example pattern:

- `Mossadegh / 1953` for distrust and reversibility memory
- `JCPOA` or `Austrian State Treaty` for architecture, inheritance, or guarantor-form questions

This pairing is often stronger than trying to make one case explain both the continuity burden and the settlement design problem.

## Vocabulary Guard

Use these terms consistently:

- `retrieval-anchored`
- `mechanism-matched`
- `falsifier-aware`
- `suggestive analogy`
- `doctrinal support`
- `ordinary-governance restatability`
- `successor carry`

Avoid looser phrases like:

- `good analogy`
- `strong comparison`
- `historically similar`

unless the example has already been demoted below anchored doctrinal support.

## Relationship To Existing Historical-Examples Audits

The existing `civ-lens/*historical-examples-audit.md` notes remain intact and useful.

Their job is to show:

- that a speaker invoked the example
- what immediate claim the speaker used it to support
- what kind of `civ-state` pattern the example may be carrying

This policy adds a stricter question:

`may the system itself now use that example as doctrinal support?`

The answer depends on the citation ladder and the four required checks above, not on speaker invocation alone.
